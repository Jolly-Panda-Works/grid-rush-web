# Grid Rush — نسخه‌ی وب (React Three Fiber + Colyseus)

بازی دونفره‌ی Tile Placement رقابتی، طبق `01_GDD.md`، `02_Core_Rules.md` و هویت بصری `21_Branding.md`.

## اجرا (لوکال)

نیازمندی: Node.js 18 یا بالاتر.

```bash
npm install
npm run dev
```

سپس `http://localhost:5176` را باز کنید. سرور Colyseus روی پورت 2567 بالا می‌آید.
برای تست دو بازیکن واقعی، دو تب (یا دو مرورگر) باز کنید و در هر دو «Find match» بزنید.

نسخه‌ی build شده (سرور خودش کلاینت را سرو می‌کند):

```bash
npm start     # build + اجرا روی http://localhost:2567
```

سایر دستورها: `npm run typecheck`، `npm run test:bots` (بازی بات‌ها با هم)، `npm run smoke -w server` (تست اتصال واقعی Colyseus؛ سرور باید روشن باشد).

## جریان بازی

1. **Loading**: فونت‌ها، بررسی سلامت سرور، نکته‌ی آموزشی.
2. **Menu**: نام، سطح، XP، رتبه، «Find match»، «Play vs bot»، راهنما، تنظیمات (صدا / Reduce motion).
3. **Matchmaking**: `joinOrCreate` در Colyseus. اگر طی ۷ ثانیه حریف پیدا نشود بات اضافه می‌شود (`MATCH_WAIT_MS` با متغیر محیطی قابل تغییر است).
4. **Game**: صفحه‌ی ۹×۹ هر دو بازیکن + مسیر زمان مشترک سه‌بعدی + HUD.
5. **Results**: ریز امتیاز (سکه‌ها ÷ ۲، رو به پایین + بونوس ۷×۷ − ۲ × خانه‌ی خالی)، تغییر رتبه (Elo)، XP و سطح.

## معماری

- `shared/`: منطق قوانین (`engine.ts`)، بات (`bot.ts`)، کاشی‌ها، ثابت‌ها. سرور و کلاینت هر دو از آن استفاده می‌کنند.
- `server/`: اتاق Colyseus (`GridRushRoom.ts`) به‌صورت server-authoritative. هر حرکت در سرور اعتبارسنجی و اجرا می‌شود و state برای دو طرف broadcast می‌شود.
- `client/`: React + R3F + Zustand. ماوس: hover و کلیک. لمس: یک تپ پیش‌نمایش، تپ دوم تأیید.
- میان‌برها: `1-3` انتخاب کاشی، `R` چرخش، `F` آینه‌ی افقی، `V` آینه‌ی عمودی، `A` کار کن، `Esc` لغو.

### سختی بات
`botTierFor(level, rating)` در `shared/src/bot.ts` پنج درجه می‌دهد (Rookie تا Master). درجه‌های پایین با احتمال حرکت تصادفی و نویز بیشتر بازی می‌کنند. درجه‌های بالا پایان بازی را پیش‌بینی می‌کنند و از ساختن حفره‌های غیرقابل‌پر پرهیز می‌کنند. رتبه‌ی نمایشی بات نزدیک به رتبه‌ی بازیکن است تا Elo معنا داشته باشد.

### پیشرفت بازیکن
سطح، XP، رتبه و آمار برد/باخت در `localStorage` مرورگر ذخیره می‌شود (بدون دیتابیس).

### حساب‌ها، لیدربورد و دوستان (سرور)
- سرور یک دیتابیس SQLite دارد (`server/data/gridrush.db`، با `DB_FILE` قابل تغییر) که با SQLite داخلی Node ساخته می‌شود؛ پس سرور به **Node 22.13 یا بالاتر** نیاز دارد و ماژول native لازم نیست. روی هاست واقعی این فایل باید روی دیسک ماندگار باشد.
- هر بازیکن اول **مهمان** است: یک حساب روی سرور با توکنی که روی دستگاه ذخیره می‌شود (`/api/auth/guest`). پیشرفت (XP، برد/باخت، آمار، دستاوردها) از دستگاه همگام می‌شود و هیچ‌وقت عقب نمی‌رود. **رتبه (rating) فقط روی سرور** و فقط در بازی‌های آنلاین تغییر می‌کند تا لیدربورد قابل دستکاری از گوشی نباشد.
- **اتصال Google Play Games** (`/api/auth/google`): سرور کد یک‌بارمصرف را با گوگل عوض می‌کند. متغیرهای `GOOGLE_CLIENT_ID` و `GOOGLE_CLIENT_SECRET` (کلاینت Web در Google Cloud همان پروژه‌ی Play Games) باید روی سرور تنظیم شوند؛ بدون آن‌ها پاسخ «تنظیم نشده» است.
  - اپ اندروید پلاگین `PlayGamesAuth` را دارد (`client/android/.../PlayGamesAuthPlugin.java`، کتابخانه‌ی `play-services-games-v2`). برای فعال شدن:
    1. در Play Console بخش Play Games Services را برای اپ بسازید و **Project ID** را بردارید.
    2. در Google Cloud همان پروژه یک کلاینت OAuth از نوع **Android** (با SHA-1 کلید امضا) و یکی از نوع **Web** بسازید.
    3. در GitHub متغیرهای `PLAY_GAMES_APP_ID` (Project ID) و `VITE_PLAY_GAMES_CLIENT_ID` (کلاینت Web) را بگذارید؛ روی سرور `GOOGLE_CLIENT_ID` و `GOOGLE_CLIENT_SECRET` همان کلاینت Web.
    - تا وقتی این‌ها تنظیم نشده‌اند دکمه‌ی «اتصال به Google Play Games» غیرفعال است و بازی بدون آن کار می‌کند.
- لیدربورد (`/api/leaderboard`): بر اساس رتبه یا سطح، همه یا فقط دوستان، ۵۰ نفر اول + رتبه‌ی خودت. دوستان (`/api/friends`): افزودن با کد دوست ۶ حرفی، پذیرفتن، حذف.
- `npm test` علاوه بر قوانین، APIها را هم روی یک دیتابیس در حافظه تست می‌کند.

### موزه
- هر صفحه‌ی تمام‌شده روی همان دستگاه در «مجموعه» نگه داشته می‌شود (۲۴ تای آخر). بازیکن تا ۶ صفحه را در موزه‌ی خودش به نمایش می‌گذارد و بقیه به آن رأی می‌دهند (هر بازیکن یک رأی برای هر صفحه). هر رأی یک امتیاز موزه و ۵ XP است.
- موزه روی همان سرور بازی است (`server/src/museum.ts`، مسیرهای `/museum/...`) و در همان دیتابیس SQLite ذخیره می‌شود. اگر فایل قدیمی `server/data/museum.json` وجود داشته باشد، یک بار خودکار به دیتابیس منتقل می‌شود.
- هویت بازیکن فعلاً یک شناسه‌ی تصادفی روی دستگاه است (حساب کاربری نیست)، پس رأی‌ها در برابر تقلب محافظت نشده‌اند.
- طرح پارچه‌ای هر کاشی (`client/src/patterns.ts`) از `uid` کاشی ساخته می‌شود و فقط ظاهری است؛ روی قوانین اثری ندارد.

## واژه‌ها: روز و خرده‌کاشی

بازی با واژه‌های [docs/days-and-shards.md](docs/days-and-shards.md) حرف می‌زند. **قانون‌های PvP عوض نشده‌اند**، فقط اسم‌ها و نمایش. در کد و سندهای قدیمی‌تر هنوز اسم‌های قبلی هست:

| در بازی | در کد و سندهای قبلی |
|---|---|
| خرده‌کاشی | سکه‌ی داخل مسابقه (`coins`) |
| روز / روزهای کاشی | جایگاه روی مسیر زمان (`pos`) / هزینه‌ی زمان (`timeCost`) |
| مهلت (۵۴ روز)، تقویم | طول مسیر (`TRACK_LENGTH`)، مسیر زمان |
| کار کن | Advance |
| روز مزد / مزد کاشی | خزانه (`TREASURE_POSITIONS`) / سکه‌ی حکاکی‌شده (`engraved`) |
| روز هدیه | خانه‌ی کاشی ۱×۱ (`REWARD_POSITIONS`) |

«سکه» فقط کیف پول بازیکن است (بیرون از مسابقه: مرحله‌ها، فروشگاه، ادامه). حالت داستانی حریف ندارد: هر مرحله یک مهلت به روز دارد و «کار کن» ۱ تا ۵ روز است ([docs/story-mode.md](docs/story-mode.md)).

## نکات صادقانه

- **قانون امتیاز (تغییر نسبت به `02_Core_Rules.md`):** امتیاز نهایی = سکه‌های باقی‌مانده ÷ ۲ (رو به پایین) + پاداش ۷×۷ − ۲ × خانه‌های خالی (`COIN_SCORE_DIVISOR` در `shared/src/constants.ts`). سند قوانین باید با این قانون به‌روزرسانی شود.

- **قانون Advance (نسخه‌ی ۰.۴، تغییر نسبت به `02_Core_Rules.md`):** بازیکن دقیقاً به «موقعیت حریف + ۱» می‌رود و به‌ازای هر خانه‌ی جابه‌جاشده ۱ سکه می‌گیرد. فرمول قبلی (`Position + Opponent + 1`) حذف شد. این تغییر حلقه‌ی خودتقویت‌شونده را از بین می‌برد. بخش ۳.۲ و ۴.۳ سند قوانین و GDD باید با این قانون به‌روزرسانی شوند.
- در خودبازی بات‌ها (`npm run test:bots`) درجه‌های بالاتر به‌طور محسوس بیشتر می‌برند (Rookie حدود ۳۸ برد، Master حدود ۷۷ برد در ۳۰۰ بازی). تنظیم دقیق سختی نیاز به پلی‌تست انسانی دارد.

## موبایل، اندروید و بیلد خودکار

**جهت صفحه:** روی موبایل (و اپ اندروید) بازی فقط **عمودی** اجرا می‌شود. اگر گوشی را بچرخانید صفحه‌ی «دستگاه را برگردان» نمایش داده می‌شود و اپ اندروید روی `sensorPortrait` قفل است. روی دسکتاپ چیدمان به اندازه‌ی پنجره تنظیم می‌شود (افقی برای پنجره‌ی پهن). پنل کاشی‌ها همیشه دیده می‌شود و در نوبت حریف فقط قفل است.

**بیلد، ورژن‌زنی و انتشار خودکار (`.github/workflows/build.yml`):** با هر push روی `main` به‌ترتیب این جاب‌ها اجرا می‌شوند: `Version` ← `Typecheck & test` ← (`Web` و `Android`) ← `GitHub Release`.

1. **ورژن خودکار از روی پیام commitها** (Conventional Commits، نسبت به آخرین تگ `vX.Y.Z`):
   - `feat!: ...` یا `BREAKING CHANGE` → **major**
   - `feat: ...` → **minor**
   - `fix:` / `perf:` / `refactor:` یا پیام بدون نوع → **patch**
   - فقط `docs:` / `chore:` / `ci:` / `test:` / `style:` / `build:` → **بدون انتشار** (فقط فایل‌های بیلد در همان run می‌ماند)
2. GitHub ورژن را در `package.json` بالا می‌برد، با پیام `chore(release): vX.Y.Z [skip ci]` commit می‌کند، تگ `vX.Y.Z` می‌زند و Release می‌سازد. اولین انتشار همان ورژن `package.json` است (`0.4.0`). اگر ورژن بالاتری را خودتان در `package.json` بنویسید، همان انتخاب می‌شود. از تب Actions با «Run workflow» هم می‌توان patch/minor/major را اجباری کرد.
3. **خروجی‌های Release:** `GridRush-X.Y.Z-Android.apk` و `.aab` (امضاشده، اگر Secretها باشند)، `GridRush-X.Y.Z-Android-debug.apk`، `GridRush-X.Y.Z-Web.zip` (آماده‌ی میزبانی روی هر هاست ایستا)، `SHA256SUMS.txt` و فهرست «What's changed» از روی commitها.
4. اندروید: `versionName` = ورژن، `versionCode` = `MAJOR*1000000 + MINOR*1000 + PATCH` (همیشه افزایشی). ورژن داخل بازی هم پایین منو دیده می‌شود.
   - شناسه‌ی اپ (package name): `com.jollypanda.grid_rush`. این شناسه بعد از انتشار نباید عوض شود.
   - **بررسی بروزرسانی:** هر بار که بازی باز می‌شود ورژن خودش را با آخرین Release گیت‌هاب مقایسه می‌کند (`client/src/update.ts`). اگر نسخه‌ی جدیدتری باشد، در اپ اندروید صفحه‌ی فروشگاه (متغیر `VITE_STORE_URL` در Variables ریپو، بعد از انتشار در فروشگاه) یا در غیر این صورت APK همان Release باز می‌شود و روی نسخه‌ی قبلی نصب می‌شود. در نسخه‌ی وب فقط یک بارگذاری دوباره پیشنهاد می‌شود. بازیکن می‌تواند «بعداً» بزند؛ آن نسخه دیگر پرسیده نمی‌شود.
   - APK دیباگ با کلید ثابت `client/android/app/debug.keystore` امضا می‌شود (عمداً داخل ریپو است، کلید دیباگ محرمانه نیست)، تا هر نسخه‌ی جدید روی نسخه‌ی قبلی نصب شود. نسخه‌های تا 0.7.0 با شناسه‌ی قدیمی و کلید تصادفی ساخته شده‌اند و یک بار باید حذف و دوباره نصب شوند.
5. Pull Request فقط ساخت آزمایشی (`X.Y.Z-dev.<run>`) انجام می‌دهد، بدون تگ و Release.

برای اینکه bump روی `main` push شود، branch protection نباید push مستقیم GitHub Actions را ببندد (Settings → Branches). در Settings → Actions → General هم «Workflow permissions» باید روی «Read and write» باشد.

**امضا:** اگر Secretهای امضا نباشند، فقط APK دیباگ ساخته می‌شود و Release با یادداشت هشدار منتشر می‌شود. برای تنظیم امضا:

1. یک keystore بسازید: `keytool -genkeypair -v -keystore gridrush.jks -alias gridrush -keyalg RSA -keysize 2048 -validity 10000`
2. در Settings → Secrets and variables → Actions این Secretها را بسازید:
   `ANDROID_KEYSTORE_BASE64` (خروجی `base64 -w0 gridrush.jks`)، `ANDROID_KEYSTORE_PASSWORD`، `ANDROID_KEY_ALIAS`، `ANDROID_KEY_PASSWORD`

keystore را جای امن نگه دارید. اگر گم شود، نمی‌توانید آپدیت همان اپ را منتشر کنید.

**نسخه‌ی فروشگاه‌ها:** وقتی Secretهای امضا تنظیم باشند، هر Release دو فایل جدا هم دارد:
- `GridRush-X.Y.Z-GooglePlay.aab` برای Google Play Console (Play فقط AAB قبول می‌کند).
- `GridRush-X.Y.Z-CafeBazaar.apk` برای پیشخان کافه‌بازار.

در این دو نسخه پیام «نسخه‌ی جدید» صفحه‌ی همان فروشگاه را باز می‌کند و APK را از GitHub دانلود نمی‌کند (فروشگاه‌ها اجازه‌ی نصب آپدیت از بیرون را نمی‌دهند). آدرس پیش‌فرض صفحه‌ها `play.google.com/store/apps/details?id=com.jollypanda.grid_rush` و `cafebazaar.ir/app/com.jollypanda.grid_rush` است و با Variables ریپو `PLAY_STORE_URL` و `BAZAAR_STORE_URL` عوض می‌شود. versionCode هر نسخه بزرگ‌تر از قبلی است، پس همین فایل‌ها مستقیم قابل آپلودند. برای Google Play پیشنهاد می‌شود «Play App Signing» را فعال کنید و همین keystore را به عنوان upload key معرفی کنید.

**تست:** `npm test` قوانین بازی (Advance، نوبت، خزانه، کاشی ۱×۱، ۷×۷، امتیاز، Tie-break) و بات‌ها را بررسی می‌کند و در CI قبل از هر انتشار اجرا می‌شود.

**آدرس سرور بازی (برای بازی آنلاین):** روی گوشی `localhost` معنی ندارد و سرور Colyseus باید جایی قابل‌دسترسی اجرا شود. یا در Variables ریپو `VITE_SERVER_URL` را بگذارید (متغیر قدیمی `SERVER_URL` هم کار می‌کند) (مثلاً `wss://game.example.com`)، یا خالی بگذارید تا بازیکن در منوی اپ «آدرس سرور» را وارد کند (مثلاً `192.168.1.20:2567` برای تست در شبکه‌ی خانگی). این آدرس روی دستگاه ذخیره می‌شود. برای محیط واقعی از `wss://` استفاده کنید.

اگر ریشه‌ی ریپوی شما همین پوشه نیست، پوشه‌ی `.github` باید در ریشه‌ی ریپو باشد و مسیرهای `client/...` در workflow با زیرپوشه هماهنگ شوند.

باز کردن پروژه در Android Studio: `npm run build -w client` سپس `npm run cap:sync -w client` و `npm run android:open -w client`.
